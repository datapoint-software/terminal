# Product

What the application does and why. This document grows as the product is designed: settled points go in the sections below and in the [decision log](#decision-log); agreed features are under [features](#features); everything else stays under [open questions](#open-questions) until it's decided.

## Vision

A terminal you can delegate to without losing sight of it. You describe what you want in a chat, and an agent works in the same terminal you're looking at: you see every command it runs and everything it reads, in the terminal or listed in the chat, and you can step in at any moment just by typing.

## Core concepts

- **Application:** Datapoint Terminal ("Terminal" for short), a desktop application for macOS, Linux and Windows.
- **Provider:** the AI service behind the agent, used with the user's own account: Anthropic or OpenAI with the user's API key, or an open-weight model the user runs themselves (e.g. with Ollama, LM Studio or vLLM) or reaches through a hosting service, over an OpenAI-compatible API. Open-weight models are supported from the first release; the model must support tool calling, a short list of tested models is kept, and choosing an untested one shows a warning. A model the user marks as local is shown as such, so the user knows nothing leaves their machine or network. The first tested model is Claude Opus 5.5, and models below a minimum context window get a warning.
- **Workspace:** a folder holding the technical documentation for a set of machines, typically one customer's or one team's infrastructure: its hosts and their labels, a document and maintenance log for each host, skills, and instructions for the agent. It holds infrastructure documentation only, never customer data. Each workspace opens in its own window, and a switcher at the top of the sidebar moves between them; a default workspace lets someone start without setting anything up. A team shares a workspace by keeping its folder wherever it already shares files (OneDrive or SharePoint, a network drive, Git or SVN); the application has no sync or version control features of its own, and a team service may come later. The folder has a fixed layout:

  ```
  acme/
    workspace.json                     hosts, their environments and labels, default approval modes and models
    TERMINAL.md                        instructions for the agent
    .terminalignore                    files never sent to the AI provider (optional; also read from the home folder down)
    hosts/web-1/README.md              a host's document
    hosts/web-1/log/                   its maintenance log, one file per entry
    skills/patch-and-reboot/SKILL.md   a skill, with any files it needs
  ```

  `workspace.json` never holds secrets. Everything personal stays in the application's own data, by workspace, never in the folder: the agent's memory, conversation history, scrollback, session recordings, the host keys last seen, and the copies of instructions and skills the user last accepted. A synced or committed folder therefore can't carry terminal output, and no database lives where a sync service could corrupt it.
- **Sidebar:** lists the workspace's hosts, its skills and its instructions, by name, without file extensions. Files are created by the application and the agent (a host's document when the host is added, a skill when one is saved); the sidebar opens and edits them but doesn't create, rename or delete files.
- **Global files:** `~/.datapoint-terminal/` holds the user's own instructions for every workspace (`TERMINAL.md`) and the default workspace (`default/`), at the same path on every platform. The application's settings and personal data stay in the operating system's application data folder.
- **Instructions:** the agent reads the user's own `TERMINAL.md`, then the workspace's, capped at 32 KB together; the chat says when they were cut short. Nothing else is read as instructions: not parent folders, `AGENTS.md`, or instruction files on remote hosts, which the agent can read as data.
- **Changes from outside:** a workspace folder can change under the user (a teammate, a sync service, a `git pull`), and the application treats such changes by what they can do:
  - **Instructions and skills** say what the agent will do, so a change to them waits for the user. The application keeps its own copy of each as the user last accepted it, shows what changed (marking a rollout made less careful), and keeps the agent on the accepted copy until the user accepts the change. A workspace the user didn't create in the application shows its instructions, skills and hosts for review the first time it's opened; until then they're given to the agent as data, and no connection opens automatically.
  - **Host settings** in `workspace.json` can only get stricter on their own: the application keeps its own record of each host's environment label, labels, default approval mode, address, user and port as the user last confirmed them, applies stricter changes, and holds looser or redirecting ones (e.g. production to development, Ask to Auto, a new address) for review, keeping the stricter value until then.
  - **Host documents** are a record of what happened, read by the agent as data, so changes to them apply at once.
  - **Conflicting copies:** when a sync service keeps two versions of one file (e.g. `README-LAPTOP.md` beside `README.md`), the application shows them as one item to settle, the agent reads neither until it's settled, and when the versions change different lines both changes can be kept in one step. One file per maintenance log entry keeps two people's logs from ever colliding.
  - **Writes are atomic:** the application writes a file in full under a temporary name outside the workspace, then moves it into place, so a sync service never uploads half a file. When the workspace is on another disk than the application's data, the temporary file is on that disk, under a name sync services skip.
- **Terminal session:** a shell the application runs, either locally (e.g. `/bin/bash`) or on a remote host over SSH.
- **Layout:** each workspace window shows the sidebar on the left and, beside it, three areas the user arranges by dragging their headers: the workspace's chat (Agent), the workspace's terminals as tabs, and open documents as tabs. By default the chat is the main area, with the terminals docked to its right and documents below them. Dropping a header on an edge of another area puts it there, and near an edge of the window docks it along that whole edge; the place it would take is highlighted until it's dropped, and Escape cancels. The View menu does the same from the keyboard (Move Agent, Move Terminals, Move Documents) and resets the layout. A move that would leave an area too small to use is refused with a note. The layout and the sizes the user drags the dividers to are the same in every window and remembered by the application. The documents area is there only while a document is open, and keeps its place for the next one. The conversation reads as a centred column however wide its area is. A shortcut hides and shows the terminals, and they show again as soon as the agent asks to run a command or runs one, so the user always sees what it types. F6 moves the keyboard between the chat, the terminals and the documents. The window's title shows the workspace; each tab's title shows its connection and environment label.
- **Agent:** the AI the user talks to in the chat pane. Each workspace has one agent, which works across the workspace's terminals and holds one conversation at a time; past conversations are kept. It can:
  - reply in the chat;
  - ask the user questions when it needs a decision, including multiple-choice questions;
  - type into any of the workspace's terminals to carry out a task, and report back. Every action names the terminal it's for, and the agent can open a terminal for one of the workspace's hosts, which is shown in the chat and needs approval in Ask mode.
- **Shared terminal:** the agent and the user share the same terminal, and it is never locked. Everything the agent sends is visible as it happens, and the agent reads any new output before deciding its next step. A mark in the margin of each command shows whether the agent or the user typed it; clicking an agent's mark goes to the chat step that sent it.
- **Agent status:** the chat pane's header always shows what the agent is doing: thinking, running a command, waiting for approval, waiting for the user's input, interrupted, or idle. A tab shows when the agent is acting in it or waiting for the user there, and the window shows it too, so a background window that needs the user stands out. The agent never switches the tab the user is looking at; each command in the chat links to its terminal.
- **Work outside the terminal:** over SSH, the agent can also run checks on separate channels, read and write files directly, and survey hosts without typing into the terminal. Every such action is listed in the chat as it happens, with its output a click away, and follows the same approval modes.
- **Whole commands:** the agent sends each command as a complete line in one go, never character by character, so the user's typing can't get mixed into a half-written command.
- **Clean prompt:** the agent types a command only when shell integration reports an idle prompt with nothing typed on it and no program running; otherwise it says why in the chat and waits. Before each command it checks the current folder, user and host again, since the user may have changed them.
- **Interrupt by typing:** as soon as the user types into any of the workspace's terminals (any key, or a paste), the agent stops. The keystroke still reaches the terminal. Scrolling, selecting and copying don't interrupt. A Stop button in the chat pane also interrupts the agent, including while it waits for the user to answer a prompt. The agent leaves any running command alone, says in the chat that it was interrupted, and holds for further instructions. A Continue button resumes the task; the agent is first told what the user typed in the meantime.
- **Input from the user:** when the agent needs something from the user, it asks in the chat. For a secret asked for in the session (a `sudo` password, a key's passphrase, a token), it never asks for the secret itself: it asks the user to type it into the terminal, so it never passes through the chat or the model. Logging in to an SSH connection (host-key confirmations, passwords and passphrases) happens in the application's own windows, never in the terminal or the chat.
- **Awaited input:** when the agent has asked the user to type something into the terminal, the user's typing is the expected answer, not an interruption. The agent doesn't read what the user types there, even if the program shows it, and carries on by itself once the prompt is answered and the program prints new output. After that, typing interrupts it as usual.
- **Shell integration:** hidden markers the shell prints to show where each prompt starts, where each command starts and how it ended, with its exit code. The application uses them to know when a command has finished or a program is waiting for input, for bash, zsh, fish and PowerShell. Where they aren't available (e.g. in cmd, or when a host's login shell isn't one of these), it falls back to judging from the output. The application loads shell integration into each session's shell as it starts, locally and over SSH, without writing any file on the host and without typing anything into the terminal; it installs it permanently only if the user asks. The chat notes that shell integration was enabled for the session.
- **Full-screen programs:** in programs such as `vim`, `less` or `top`, the agent reads the screen and sends keys; in Ask mode it proposes the keys before sending them. It prefers commands that don't open such programs, e.g. `git --no-pager` or `PAGER=cat`.
- **Output sent to the provider:** while the agent works on a task, new output is sent as it comes. Between tasks nothing is sent; with the user's next message, only the output since the last task goes along, and the chat says how much before sending. Very long output, beyond a limit based on the model's context window that the user can change in settings, is cut down to its start and end, and the agent can ask for the rest when it needs it. The user can see exactly what was sent to the provider at each step.
- **Approval modes:** how freely the agent may run commands and change files. There is one mode for the agent, across every terminal of the project, production included; the user picks it in the chat and can change it at any time, and it applies from the agent's next command. Each project remembers its last mode; a new project starts in Ask. Approval requests show the terminal's name and environment label prominently:
  - **Ask** (default): the agent proposes each command and the user approves it before it runs.
  - **Ask if risky:** the agent runs read-only commands on its own and asks before anything that changes a system.
  - **Plan:** the agent runs read-only commands on its own; before changing anything it shows a plan, whose steps then run without asking. Anything outside the plan asks, as do the few commands that always need the user (decision 84) and, once web text is in the conversation, commands that reach other machines (decision 106).
  - **Ignore permissions:** the agent runs every command without asking. Choosing it needs a confirmation every time, it's never remembered, and it ends with the conversation or when the application closes. Web searches and page reads still ask, as do commands that name files the project keeps from the agent (`.terminalignore`); secret masking and the block on private addresses stay on.

  Approving takes a deliberate action, a button or a shortcut that typing can't trigger (not Enter alone), and an approval request never takes keyboard focus away from the terminal; screen readers announce it. The user can edit a proposed command before approving it, and the agent sees the edited version.
- **Tabs:** each tab in a workspace window is one terminal session or one open document.
- **Connection:** where a terminal session runs: the local machine, an SSH host, or a container on either. A workspace lists its hosts in `workspace.json`, by `Host` from `~/.ssh/config` or by host, user and port, each with an environment label and any number of free-form labels (e.g. `web`, `debian`), which skills use to choose where they run. Several tabs can use the same host, and the same host can belong to several workspaces. A host from `~/.ssh/config` that the workspace doesn't list can still be opened, with an offer to add it; until it's added, the agent writes no documentation for it.
- **Memory:** the user's preferences, which the agent remembers across sessions: some for every workspace (e.g. "use `doas`, not `sudo`"), some for one workspace. Memory is personal: it's kept in the application's own data, never in a workspace folder, so it isn't shared with the team. Facts about a machine go into its host document, which the team shares, not memory. The agent writes memory on its own and says so in the chat; the user can view, edit, delete and clear it in Settings › Memory at any time, and instructions take precedence over it.
- **Host documentation:** besides memory, the agent keeps documentation for each of the workspace's hosts, in `hosts/<name>/`, written for people to read: `README.md` says what the machine is (e.g. OS and version, hardware) and what's installed and running (e.g. key packages and services), and `log/` holds the maintenance log, one file per entry, of what was done on it, when, why and by whom. A standard set of sections gives every host the same starting shape, but it isn't a fixed schema: the agent and the user can add sections for whatever a host needs. It is separate from memory, and the agent reads both. Documentation belongs to the workspace: the same server in two workspaces has separate documentation. The agent updates it after any task that changes the system, says so in the chat, and leaves the user's own edits alone; the user can also ask it to survey and document a host in full.
- **Skill:** a reusable procedure, in the open Agent Skills format: a folder in `skills/` whose `SKILL.md` gives, in its header, a name, a one-line description, where it runs and how it rolls out, and in its body, the steps. Where it runs and how it rolls out go under the header's `metadata` map, which the format keeps for a client's own fields, as `terminal.labels`, `terminal.rollout`, `terminal.batch-size`, `terminal.max-hosts`, `terminal.health-check`, `terminal.healthy-for`, `terminal.timeout` and `terminal.on-failure`, so the file stays valid for other tools. The agent sees only each skill's name and description until a task needs one, then reads it in full; files bundled with a skill are read as needed, and anything run from them is typed into a terminal like any command.
  - **Where it runs:** on the hosts that have every label the skill lists, or on all hosts when it lists none. The skill's page names the hosts that match.
  - **How it rolls out:** one host at a time, in batches of a set size, or all at once up to a set number of hosts. After each host or batch, a health check runs in that host's terminal and must keep passing for a set time before the next host starts, within a time limit; if a host fails, the rollout stops, continues with the next host, or asks the user, as the skill says. The application enforces the rollout, not the model, and a rollout starts like any other task: the agent shows its plan with the hosts, the order and the check, and the user approves it. When a host reboots, its SSH terminal reconnects on its own and waits for the host to come back before the check runs.
  - **Where skills come from:** after a task, the agent offers to save it as a skill, or the user asks it to write one; the user edits a skill's page like any document.
- **Secrets in workspace files:** the agent never writes a secret into a workspace's files: everything it writes there goes through the secret detector and is refused if anything matches. Files the user writes are never changed. When a file the agent is about to send to the provider looks like it holds a secret, the agent pauses and shows the match; the user chooses to send it masked, send it as written, or skip the file, and can mark a match as not a secret, which is remembered (in the application's own data). `.terminalignore` files, in `.gitignore` syntax, in any folder from the home folder down (or from the workspace's folder, when it's outside the home folder), list files the application never reads or sends. The agent is told not to read them, and a command that names one always asks first, in every mode; what a command prints in the terminal is protected only by secret detection, since output can't be traced to the file it came from. Detection is a best guess: it recognizes known key formats, passwords in addresses, assignments such as `password=…` or `DB_PASS=…` and secrets the application already knows, but can miss a password written in prose. `.terminalignore` is the user's reliable control over what the application reads; for the terminal, approving commands is.

## Users

Developers and system administrators who already use a terminal every day. People new to the command line aren't the first audience: they need more guidance and safety design, which can be added later.

## Features

Features agreed while brainstorming, beyond the core concepts above. All of them are in the first release.

### A good terminal first

- Split panes, scrollback search, themes, fonts and the keyboard shortcuts users expect from their current terminal.
- Desktop notifications when the agent finishes a long task or is waiting for the user.

### Workspaces, hosts and skills

- **Sidebar:** the workspace switcher at the top shows the workspace's name, where its folder is and how many hosts it has; it lists the other workspaces, with New Workspace…, Open Workspace Folder…, Show in Finder (or the file manager) and Rename. Then:
  - **Hosts:** the workspace's hosts, each with a dot for its environment and how many terminals are open on it; hosts from the user's SSH configuration that aren't in the workspace fold into one line, each with Add. Selecting a host opens its document.
  - **Skills:** each skill with the number of hosts it runs on; a skill changed from outside shows Review.
  - **Workspace:** Instructions.
  - **Settings** at the bottom.
- **Add a Host:** name, address, user and port, environment and labels; the labels already used in the workspace are offered as suggestions.
- **Host documents:** a host's document shows its environment, labels, address and open terminals above it, with Open terminal, then its `README.md` and its maintenance log, newest first, each entry with its date and who did it.
- **Skill pages:** a skill opens as a page: where it runs and how it rolls out as a form above (the labels, with the hosts they match; the order; the health check; how long it must stay healthy; when to give up; what to do if a host fails), then its description and steps as a document. Run on N Hosts… starts the task in the chat for the user to send.
- **Rollouts:** while a skill runs on several hosts, a card pinned above the conversation lists each host as done, running, checking health (with a progress bar), failed or not started, with the health check, Pause After This Host and Stop. When a host fails and the skill says to ask, the agent asks with the usual question card: stop, check again, skip the host and go on, or something else.
- **Review of changes from outside:** a sheet shows what changed in a skill's rollout and steps, or in the instructions, with Keep My Version and Accept Change; conflicting copies show the two versions side by side, with Keep Both Changes when they change different lines.
- **Document editor:** Markdown files open in a rich editor, edited as the rendered document. Formatting comes from Markdown typed as you go, the usual shortcuts, a menu on the selected text and a Format menu in the menu bar; there's no toolbar. The editor keeps the file's Markdown exactly as written, including the hidden markers around the agent's sections; those sections look like the rest of the document, and edits in them may be replaced at the agent's next update. Documents open as tabs after the terminals. The block being edited (a paragraph, a heading, one list item) shows its Markdown at the same size, and everything else stays rendered; View › Show Markdown shows the whole file as text. Changes save as you type. When the agent updates an open document, it reloads if the user has no unsaved changes; otherwise a bar lets them keep theirs or take the agent's.
- **Settings › Memory:** what the agent remembers, for every workspace and for the current one, each entry with when and where it was learned, Edit and Delete, and Clear… for each group.
- **Files on hosts:** a text or configuration file on a terminal's machine opens in an editor with syntax highlighting for the common formats, and is saved through that terminal after a review of the change.

### Safety on real servers

- **Environment labels:** mark a connection profile as production, staging or development; production tabs are clearly colored and default to Ask.
- **Read-only commands:** a shipped list of reading commands runs without asking in "Ask if risky" mode, in Plan mode before a plan and while the agent looks; the user can teach more from an approval card or in Settings › Commands, kept in their own settings (decision 112).
- **Look, then plan:** before planning a change, the agent asks to look at the hosts involved, saying for each what it will look for and why; once allowed, its read-only commands there run without asking until the task ends (decision 111).
- **Plan before changing:** for a task that changes the system, the agent first shows its plan: what it found, then each step with a title, the hosts it runs on, why, and the command (or an example of it), a step that's risky or hard to undo is flagged (by the agent, and by the application from the command itself, e.g. a reboot that ends the connection), and how to roll back is always in view. The plan opens as a page in the documents area, where the user can comment on any part of it and send it back to be revised, with the changed steps marked. Once approved, the plan is pinned above the conversation while the task runs, with a progress bar and each step marked running, done or failed (with its exit code); it folds to one line, and each planned command in the conversation says which step it is. When the task ends, it unpins and stays where it was approved, folded to its result. If the agent needs a step the approved plan doesn't include, it stops and says so before going further.
- **Questions:** the agent's question names the terminal it's about, gives what the user needs to decide, then the question in bold, and its choices as one list, each with a line on what it does and the agent's recommendation tagged. A choice is a click, or its number key while the card has focus; the last row, "Something else…", opens a box for an answer in the user's own words. Once answered, the question stays in the conversation as a quiet line, followed by the answer.
- **Changing course:** the message box stays open while the agent waits on a card (a question, a plan, a command or anything else to approve). Sending a message then cancels the card: nothing it proposed runs, an approved plan no longer applies, and the agent takes the message as the new goal, keeping what it already learned in the conversation.
- **Automatic backups:** before editing a configuration file, the agent keeps a copy, so any change can be undone.
- **Edits as diffs:** the agent proposes file changes as a diff to approve, rather than editing through `sed` or an editor.
- **Secret redaction:** output is checked for things that look like keys and tokens, which are masked before anything is sent to the provider.
- **Session recording:** a replayable record of each session, showing who typed what (the user or the agent) and what the agent did outside the terminal, for reviews and handovers. It is the user's own record, not a tamper-proof audit log (decision 75).

### Sysadmins

- **Skills:** save a completed task as a reusable procedure (e.g. renewing certificates, rotating logs), with where it runs and how it rolls out, and run it again on the hosts it matches.
- **Several hosts at once:** the workspace's agent rolls a task out across several of the workspace's terminals, following a skill's rollout when there is one, and otherwise to one host first, then the rest, stopping at the first failure. In Ask mode, approving a command on the first host approves the identical command on the others. Each host gets its own maintenance log entry. The agent can also write and run tools sysadmins already use for fleets (e.g. Ansible) from a single terminal.
- **Watch and alert:** ask the agent to watch a command or log until something happens (a deployment finishes, an error appears) and report back.
- **SSH essentials:** jump hosts, port forwarding and file transfer, configured per connection profile.
- **Containers:** treat a Docker container or a Kubernetes pod as a connection, with its own documentation.

### Developers

- **Explain and fix:** select output in the terminal, or click a failed command, and ask the agent to explain it or fix it.
- **Git help:** review a diff, write commit messages, resolve merge conflicts.

### Cost and control

- **Usage display:** tokens and estimated cost per session and per tab, with an optional budget limit. Input read from the provider's prompt cache is counted and priced at its own, lower rate, and the session's details say how much of the input came from the cache.
