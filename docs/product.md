# Product

What the application does and why. This document grows as the product is designed: settled points go in the sections below and in the [decision log](#decision-log); agreed features are under [features](#features); everything else stays under [open questions](#open-questions) until it's decided.

## Vision

A terminal you can delegate to without losing sight of it. You describe what you want in a chat, and an agent works in the same terminal you're looking at: you see every command it runs and everything it reads, in the terminal or listed in the chat, and you can step in at any moment just by typing.

## Core concepts

- **Application:** Datapoint Terminal ("Terminal" for short), a desktop application for macOS, Linux and Windows.
- **Provider:** the AI service behind the agent, used with the user's own account: Anthropic or OpenAI with the user's API key, or an open-weight model the user runs themselves (e.g. with Ollama, LM Studio or vLLM) or reaches through a hosting service, over an OpenAI-compatible API. Open-weight models are supported from the first release; the model must support tool calling, a short list of tested models is kept, and choosing an untested one shows a warning. A model the user marks as local is shown as such, so the user knows nothing leaves their machine or network. The first tested model is Claude Opus 5.5, and models below a minimum context window get a warning.
- **Project:** a folder on the user's file system that holds everything for a piece of work: instructions, the agent's memory, host documentation, runbooks, and any other files the user or the agent writes (e.g. scripts, reports). Any folder can be a project, including a Git repository or a folder inside one; whether it's under version control is up to the user, and the application has no Git features. A folder is a project once it has a `.terminal.json` file or a `.terminal/` folder; opening any other folder as a project creates `.terminal/`, and `.terminal.json` is created only once there's a shared setting to save. Each project opens in its own window. A default project lets someone start without setting anything up.

  ```
  my-project/
    TERMINAL.md          the user's instructions (optional; AGENTS.md also works)
    .terminalignore      files the application never reads or sends (optional, in any folder)
    .terminal.json       shared settings: connections, environment labels, default approval modes and models
    hosts/web-1.md       documentation, one file per connection
    runbooks/            saved procedures
    .terminal/           personal: the agent's memory, conversation history, scrollback, host keys last seen
  ```

  `.terminal.json` is meant to be shared with the project and never holds secrets. `.terminal/` is personal: when the project is in a Git repository whose ignore rules don't cover it, the application offers to add `.terminal/` to `.gitignore`.
- **Global files:** `~/.datapoint-terminal/` holds the user's global instructions (`TERMINAL.md`), the agent's global memory (`MEMORY.md`) and the default project (`default/`), at the same path on every platform. The application's own settings stay in the operating system's application data folder.
- **Instructions:** the agent reads instruction files from the project's folder and each of its parents up to the user's home folder: in each folder, `TERMINAL.md`, or `AGENTS.md` where there's no `TERMINAL.md`. A project outside the home folder reads only its own folder. The global `TERMINAL.md` comes first, then the broadest folder down to the project's, so nearer files take precedence; each file is read once. Instruction files are capped (32 KB in all), and the chat says when they were cut short. Instruction files on remote hosts aren't read as instructions; the agent can read them as data.
- **Trust:** a project's instruction files and memory count as instructions only once the user trusts the project. The first time a folder the application didn't create is opened, the user sees every instruction file that would be read and the connections in `.terminal.json`, and chooses to trust it or open it without trusting; untrusted, the files are given to the agent as data, like terminal output, and no connection opens automatically. Trust is remembered in the application's own data, never in the project, and is asked again when a new instruction file appears or the folder moves. The default project and projects created in the application are trusted.
- **Changes from outside:** a project folder can change under the user (a `git pull`, a sync service, a teammate). Such changes can make things stricter on their own, never looser: the application keeps its own record of each connection's environment label, default approval mode, host, user and port as the user last confirmed them, applies stricter changes, and holds looser or redirecting ones (e.g. production to development, Ask to Auto, a new address) for the user to review, keeping the stricter value until then. A changed instruction file is noted in the chat with its changes a click away.
- **Terminal session:** a shell the application runs, either locally (e.g. `/bin/bash`) or on a remote host over SSH.
- **Layout:** each project window shows the project's terminals as tabs, with the project's chat pane beside them, docked to the right, left, top or bottom. The side is set for the whole application and can be changed per window; a shortcut hides and shows the pane. The window's title shows the project; each tab's title shows its connection and environment label.
- **Agent:** the AI the user talks to in the chat pane. Each project has one agent, which works across the project's terminals and holds one conversation at a time; past conversations are kept. It can:
  - reply in the chat;
  - ask the user questions when it needs a decision, including multiple-choice questions;
  - type into any of the project's terminals to carry out a task, and report back. Every action names the terminal it's for, and the agent can open a terminal for one of the project's connections, which is shown in the chat and needs approval in Ask mode.
- **Shared terminal:** the agent and the user share the same terminal, and it is never locked. Everything the agent sends is visible as it happens, and the agent reads any new output before deciding its next step. A mark in the margin of each command shows whether the agent or the user typed it; clicking an agent's mark goes to the chat step that sent it.
- **Agent status:** the chat pane's header always shows what the agent is doing: thinking, running a command, waiting for approval, waiting for the user's input, interrupted, or idle. A tab shows when the agent is acting in it or waiting for the user there, and the window shows it too, so a background window that needs the user stands out. The agent never switches the tab the user is looking at; each command in the chat links to its terminal.
- **Work outside the terminal:** over SSH, the agent can also run checks on separate channels, read and write files directly, and survey hosts without typing into the terminal. Every such action is listed in the chat as it happens, with its output a click away, and follows the same approval modes.
- **Whole commands:** the agent sends each command as a complete line in one go, never character by character, so the user's typing can't get mixed into a half-written command.
- **Clean prompt:** the agent types a command only when shell integration reports an idle prompt with nothing typed on it and no program running; otherwise it says why in the chat and waits. Before each command it checks the current folder, user and host again, since the user may have changed them.
- **Interrupt by typing:** as soon as the user types into any of the project's terminals (any key, or a paste), the agent stops. The keystroke still reaches the terminal. Scrolling, selecting and copying don't interrupt. A Stop button in the chat pane also interrupts the agent, including while it waits for the user to answer a prompt. The agent leaves any running command alone, says in the chat that it was interrupted, and holds for further instructions. A Continue button resumes the task; the agent is first told what the user typed in the meantime.
- **Input from the user:** when the agent needs something from the user, it asks in the chat. For a secret asked for in the session (a `sudo` password, a key's passphrase, a token), it never asks for the secret itself: it asks the user to type it into the terminal, so it never passes through the chat or the model. Logging in to an SSH connection (host-key confirmations, passwords and passphrases) happens in the application's own windows, never in the terminal or the chat.
- **Awaited input:** when the agent has asked the user to type something into the terminal, the user's typing is the expected answer, not an interruption. The agent doesn't read what the user types there, even if the program shows it, and carries on by itself once the prompt is answered and the program prints new output. After that, typing interrupts it as usual.
- **Shell integration:** hidden markers the shell prints to show where each prompt starts, where each command starts and how it ended, with its exit code. The application uses them to know when a command has finished or a program is waiting for input, for bash, zsh, fish and PowerShell. Where they aren't available (e.g. in cmd, or when a host's login shell isn't one of these), it falls back to judging from the output. The application loads shell integration into each session's shell as it starts, locally and over SSH, without writing any file on the host and without typing anything into the terminal; it installs it permanently only if the user asks. The chat notes that shell integration was enabled for the session.
- **Full-screen programs:** in programs such as `vim`, `less` or `top`, the agent reads the screen and sends keys; in Ask mode it proposes the keys before sending them. It prefers commands that don't open such programs, e.g. `git --no-pager` or `PAGER=cat`.
- **Output sent to the provider:** while the agent works on a task, new output is sent as it comes. Between tasks nothing is sent; with the user's next message, only the output since the last task goes along, and the chat says how much before sending. Very long output, beyond a limit based on the model's context window that the user can change in settings, is cut down to its start and end, and the agent can ask for the rest when it needs it. The user can see exactly what was sent to the provider at each step.
- **Approval modes:** how freely the agent may run commands and change files, chosen per terminal, so in one task a development terminal can run more freely while production still asks. Each connection has a default mode, and connections labeled production default to Ask; the user can change a terminal's mode at any time, and it applies from the agent's next command there. Approval requests show the terminal's name and environment label prominently:
  - **Ask** (default): the agent proposes each command and the user approves it before it runs.
  - **Ask for risky commands:** the agent runs read-only commands on its own and asks before anything that changes the system.
  - **Auto:** the agent runs every command without asking, except the few that always need the user (decision 84). Auto lasts for the current task, then the terminal returns to its connection's default mode; on a production connection, choosing it needs a confirmation.

  Approving takes a deliberate action, a button or a shortcut that typing can't trigger (not Enter alone), and an approval request never takes keyboard focus away from the terminal; screen readers announce it. The user can edit a proposed command before approving it, and the agent sees the edited version.
- **Tabs:** each tab in a project window is one terminal session.
- **Connection:** where a terminal session runs: the local machine, an SSH host, or a container on either. A project lists the connections it uses in `.terminal.json`, by `Host` from `~/.ssh/config` or by host, user and port; several tabs can use the same connection, and the same host can belong to several projects. A host from `~/.ssh/config` that the project doesn't list can still be opened, with an offer to add it; until it's added, the agent writes no documentation for it.
- **Memory:** the user's preferences, which the agent remembers across sessions: `~/.datapoint-terminal/MEMORY.md` for preferences everywhere (e.g. "use `doas`, not `sudo`"), and `.terminal/MEMORY.md` for one project. Facts about a machine go into its host documentation, not memory. The agent writes memory on its own and says so in the chat, with a link to the file; the user can view, edit and clear it at any time, and the user's own instruction files take precedence over it.
- **Host documentation:** besides memory, the agent keeps documentation for each of the project's connections, in the project's `hosts/` folder, one Markdown file per connection, written for people to read: what the machine is (e.g. OS and version, hardware), what's installed and running (e.g. key packages and services), and a maintenance log of what was done on it, when and why. A standard set of sections gives every host the same starting shape, but it isn't a fixed schema: the agent and the user can add sections, or further documents, for whatever a host needs. It is separate from memory, and the agent reads both. Documentation belongs to the project: the same server in two projects has separate documentation. The agent updates it after any task that changes the system, says so in the chat, and leaves the user's own edits alone; the user can also ask it to survey and document a host in full.
- **Secrets in project files:** the agent never writes a secret into a project's files: everything it writes there goes through the secret detector and is refused if anything matches. Files the user writes are never changed. When a file the agent is about to send to the provider looks like it holds a secret, the agent pauses and shows the match; the user chooses to send it masked, send it as written, or skip the file, and can mark a match as not a secret, which is remembered (in the application's own data). `.terminalignore` files, in `.gitignore` syntax, in any folder of the project or above it up to the home folder, list files the application never reads or sends. The agent is told not to read them, and a command that names one always asks first, in every mode; what a command prints in the terminal is protected only by secret detection, since output can't be traced to the file it came from. Detection is a best guess: it recognizes known key formats, passwords in addresses, assignments such as `password=…` or `DB_PASS=…` and secrets the application already knows, but can miss a password written in prose. `.terminalignore` is the user's reliable control over what the application reads; for the terminal, approving commands is.

## Users

Developers and system administrators who already use a terminal every day. People new to the command line aren't the first audience: they need more guidance and safety design, which can be added later.

## Features

Features agreed while brainstorming, beyond the core concepts above. All of them are in the first release.

### A good terminal first

- Split panes, scrollback search, themes, fonts and the keyboard shortcuts users expect from their current terminal.
- Desktop notifications when the agent finishes a long task or is waiting for the user.

### Safety on real servers

- **Environment labels:** mark a connection profile as production, staging or development; production tabs are clearly colored and default to Ask.
- **Plan before changing:** for a task that changes the system, the agent first shows its plan: each step says what it does and the exact command, a step that's risky or hard to undo is flagged (by the agent, and by the application from the command itself, e.g. a reboot that ends the connection), and how to roll back is always in view. Once approved, the plan stays in the conversation as a checklist that marks each step running, done or failed. If the agent needs a step the approved plan doesn't include, it stops and says so before going further.
- **Automatic backups:** before editing a configuration file, the agent keeps a copy, so any change can be undone.
- **Edits as diffs:** the agent proposes file changes as a diff to approve, rather than editing through `sed` or an editor.
- **Secret redaction:** output is checked for things that look like keys and tokens, which are masked before anything is sent to the provider.
- **Session recording:** a replayable record of each session, showing who typed what (the user or the agent) and what the agent did outside the terminal, for reviews and handovers. It is the user's own record, not a tamper-proof audit log (decision 75).

### Sysadmins

- **Runbooks:** save a completed task as a reusable procedure (e.g. renewing certificates, rotating logs) and run it again, with parameters, on any host.
- **Several hosts at once:** the project's agent rolls a task out across several of the project's terminals: to one host first, then the rest, stopping at the first failure. In Ask mode, approving a command on the first host approves the identical command on the others. Each host gets its own maintenance log entry. The agent can also write and run tools sysadmins already use for fleets (e.g. Ansible) from a single terminal.
- **Watch and alert:** ask the agent to watch a command or log until something happens (a deployment finishes, an error appears) and report back.
- **SSH essentials:** jump hosts, port forwarding and file transfer, configured per connection profile.
- **Containers:** treat a Docker container or a Kubernetes pod as a connection, with its own documentation.

### Developers

- **Explain and fix:** select output in the terminal, or click a failed command, and ask the agent to explain it or fix it.
- **Code projects:** a project can be a code repository or a folder inside one, so the repository's `TERMINAL.md` or `AGENTS.md` files guide the agent. When the agent works in a repository on a remote host, it can read that repository's instruction files and `README.md` as data.
- **Git help:** review a diff, write commit messages, resolve merge conflicts.

### Cost and control

- **Usage display:** tokens and estimated cost per session and per tab, with an optional budget limit.
